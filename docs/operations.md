# 運用ルール

看護手順書（`procedures/`）を変更して公開するまでの運用。このリポジトリのデータは架空で、
**実在の患者情報は一切持ち込まない。** 実運用データは電子カルテとは別枠（別ネットワーク・別システム）で管理する。

## 1. ブランチ運用

- `main` は公開される正本。直接 push しない（設定は [branch-protection.md](branch-protection.md)）。
- 変更は作業ブランチで行う。命名: `feat/<内容>`（追加）、`fix/<内容>`（修正）、`hotfix/<内容>`（緊急）。
- 流れ: 作業ブランチ → PR（テンプレートを埋める）→ CI 成功 → 作成者以外の承認 → `main` へマージ。
- PR は 1 つの目的に絞る。手順の内容変更と、構造・命名の変更を混ぜない。
- 手順の更新日は frontmatter の `updated` を変更時に更新する。

## 2. 承認基準

承認者は次をすべて確認してから承認する。

1. CI が成功している（命名規則・frontmatter・患者情報チェック・lint・ビルド）。
2. 変更理由が妥当で、根拠（院内規程・ガイドライン）と手順の内容が一致している。
3. 本文に患者情報がない。
4. **画像をすべて目視した。** 患者情報チェックは画像内の文字を検出できない。モニタ表示、
   リストバンド、書類、ファイル名、EXIF も確認する。
5. 承認後に追加コミットがあれば承認は取り消される。再確認して承認し直す。

## 3. 緊急修正

誤りが臨床上の危険につながる場合のみ。**手順は短縮するが、経路（PR・CI・承認）は省略しない。**

1. `hotfix/<内容>` ブランチで最小限の修正だけを行う。
2. PR のタイトルに `[緊急]` を付け、変更理由に影響範囲を書く。
3. CI を通し、承認者 1 名の確認を得てマージする（管理者も例外にしない）。
4. 誤った記載の期間と原因を、PR 本文または別の記録に残す。
5. 後日、通常の PR で恒久対応と再発防止（チェック項目の追加など）を行う。

## 4. 患者情報を入れないルール

- 氏名・生年月日・ID・住所・連絡先・個別症例の日付や経過を、本文・画像・ファイル名・コミットメッセージ・PR コメントに書かない。
- 例示は架空の値にし、架空であることが明らかな書き方にする。
- 画像は撮影・加工の時点で患者が特定できないことを確認する。

### 混入に気づいたとき

1. **まず広げない。** 該当 PR のマージを止める（未マージなら PR を閉じる）。
2. 気づいた人が、責任者（情報管理担当）へ速やかに報告する。院内の規程に従う。
3. 未マージの場合: 作業ブランチの履歴から該当部分を完全に取り除いて force push する
   （最後のコミットで消すだけでは履歴に残る）。PR のコメント・差分・CI の Artifact も確認して削除する。
4. **マージ済みの場合:** `main` の履歴の書き換え、フォーク・クローン・Artifact・公開サイトのキャッシュの
   確認と削除が必要になる。個人判断で行わず、情報管理担当の指示に従う。
5. 原因（レビューで見落とした理由、検出ルールの不足）を記録し、チェックやテンプレートを見直す。

### 自動チェックの位置づけ

`npm run check:patient-info` は電話番号・生年月日の文脈・長い数字・メールなどを探す補助である。
**画像内の文字は検出できない。最終確認は PR レビューでの目視である。** 誤検知は
`scripts/patient-info-allowlist.json` に、対象ファイル・ルール・理由を指定して除外する
（行番号も指定できる。検査全体やルール全体の無効化はできない）。

## 5. 成果物（Artifact）の種類

| 種類 | 作るもの | 内容 | 用途 |
|---|---|---|---|
| 通常 CI の Artifact（`site-ci-out`） | `ci.yml` | `out/`（BASE_PATH 空 = ルート配信） | 検証済みビルドの確認、ルート配信のサーバーへ手で配置する元 |
| Pages 用 Artifact | `deploy-pages.yml` | `NEXT_PUBLIC_BASE_PATH=/nursing-procedures` で作った `out/` | GitHub Pages へのデプロイ専用 |

**通常 CI の Artifact をデプロイに再利用しない。** 理由: (a) BASE_PATH はビルド時に埋め込まれ、
配信先ごとに成果物が変わる。(b) PR ブランチ由来の成果物を公開経路に乗せない。公開物は常に
`main` のコードから作り直す。

## 6. デプロイ（テスト用: GitHub Pages）

- `deploy-pages.yml` を手動実行する（`workflow_dispatch`）。`main` 以外からは実行時に拒否される。
- 事前設定: Settings → Pages の Source を「GitHub Actions」にし、Environments の `github-pages` で
  対象ブランチを `main` のみにする。
- 権限は、ビルド側が `contents: read`、デプロイ側が `pages: write` と `id-token: write` のみ。独自のシークレットは使わない。

## 7. 開発補助ワークフロー（claude.yml）

`.github/workflows/claude.yml` は開発補助用で、このリポジトリの検証・公開の仕組みとは別物。
外部サービスの API キーと広い権限（`contents: write` 等）を使う。**実運用側のリポジトリには持ち込まない。**
